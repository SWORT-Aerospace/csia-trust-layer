# E2 board selection — from both projects' own trees, not from reputation

**Evidence:** `research/physical_validation/results/E2_BOARD_SURVEY.json`,
generated by `tools/csia_experiment/e2_board_survey.py` from the ArduPilot and
PX4 checkouts at the commits the survey records. 450 ArduPilot hwdef boards,
120 PX4 boards, 49 of them with SIH enabled.

---

## 1. The decision

**Board class: Pixhawk FMUv6C. Reference board: Holybro Pixhawk 6C.**

| | ArduPilot | PX4 |
|---|---|---|
| board identifier | `Pixhawk6C` | `px4/fmu-v6c` |
| support evidence | `libraries/AP_HAL_ChibiOS/hwdef/Pixhawk6C/hwdef.dat` | `boards/px4/fmu-v6c/default.px4board` |
| MCU as each tree declares it | `STM32H7xx STM32H743xx` | `STM32H743VI` |
| MCU family agrees | **yes** | **yes** |
| PX4 SIH available | — | **yes**, on the `default` target |
| firmware target name | `Pixhawk6C` | `px4_fmu-v6c_default` |
| IMUs in the ArduPilot hwdef | **4 declared**: ICM-42688-P, LSM6DSV, BMI055, BMI088 | |
| barometers | MS5611 ×2, BMP388 | |
| compasses | IST8310, RM3100 | |

**Why this one, against the ten other boards both projects support:**

1. **FMUv6C is a published Pixhawk FMU standard, not one vendor's product.**
   Several vendors build compliant boards, so availability does not depend on
   a single supplier. Every other H7 candidate in the survey
   (`CUAV-Nora`, `CUAV-X7`, `Durandal`, `KakuteH7`, `mRoControlZeroH7`,
   `mRoPixracerPro`, `MatekH743`) is a single-vendor design.
2. **Two IMUs, and more.** `redundant_imu` is a relation in the frozen trust
   graph, and **PX4 SIH publishes no `SCALED_IMU2` at all** — which is why
   PX4's E1 demonstration was narrower (1 of 4 GNSS-gated relations live, not
   3 of 4). A four-IMU board is what lets E2 test whether that narrowness was
   a property of the *simulator* or of the *platform*. That is the single most
   informative thing E2 can measure.
3. **PX4 SIH is enabled on its default target**, so the secondary execution
   mode of §3 needs no custom build.
4. `MatekH743` — the board `docs/HARDWARE_BOM.md` previously selected — is
   supported by both, but **PX4 SIH is not enabled on `matek/h743`**. It
   remains a valid choice for the primary mode and loses the secondary one.

## 2. One board or two

**One board, flashed sequentially.** ArduPilot first, full verification, then
PX4, full verification.

**Why one is methodologically preferable here:** E2's question is whether the
frozen core behaves the same against real hardware as against a simulator, with
the *stack* as the variable. Two boards would introduce a second variable —
unit-to-unit differences in sensors, soldering and calibration — into an
experiment designed to have one. That is the same confound as FL-017, where the
"repeat" varied a configuration field nobody had pinned.

**When two would be preferable, stated so the choice is reversible:** if E2
ever needs the two stacks running *simultaneously* on identical hardware, or if
sequential flashing is suspected of changing board state. Neither applies to
the E2 objective, and a second unit can be bought later without invalidating
anything.

**Sequential flashing carries one risk and it is checkable:** parameters or
bootloader state persisting across a reflash. §6 of the build packet records
the firmware version string **from the board**, and a full parameter dump goes
in the trial record, so a persistence effect is visible rather than assumed
absent.

## 3. Execution mode — and a negative finding

**PRIMARY MODE: bench-static, real sensors, no simulator.** The board runs
normal firmware, sits still with props absent, and its real IMUs, barometer,
magnetometer and GNSS produce real telemetry over a real serial link. CSIA
ingests that. This satisfies the E2 objective exactly — real flight-controller
hardware, real telemetry boundary — and it is supported identically by both
stacks, because it is just "the firmware running".

**NEGATIVE FINDING, from the survey: no board supports simulation-on-hardware
on BOTH stacks.** ArduPilot's `-SimOnHardWare` variants exist for exactly two
boards — `CubeOrange` and `CubeOrangePlus` — and **neither has PX4 SIH
enabled**. The `both_support_simulation_on_hardware` column is **false for
every one of the 15 rows**. So the tempting "run each stack's own on-board
simulator and compare" design is **not available on a common board**, and
pretending otherwise would have produced an experiment that could not be run.

**SECONDARY MODE, PX4 only: SIH on hardware.** Available on `px4/fmu-v6c` and
useful if motion-dependent relations are wanted. **It has no ArduPilot
equivalent on this board**, so any result from it is single-stack and must be
reported that way — the same asymmetry discipline the PX4 passive-link
qualification already gets.

## 4. What must be verified at purchase, because the tree cannot tell you

* the listing is a **Pixhawk 6C**, and its revision is the one both trees
  describe;
* it appears in the **current** ArduPilot firmware list and the **current** PX4
  board list — the survey is a snapshot at the commits it records;
* the unit carries the IMU set the hwdef declares. Vendors do substitute parts.

**Nothing here is priced.** Vendor sites answer 403 at CONNECT from this
environment, so every figure would be invented.

## 5. What the survey cannot support

* that firmware is currently **built and published** for the board — only that
  it is in each tree;
* availability, price, or lead time;
* that a board absent from the survey is unsupported. The intersection is
  computed over a hand-written alias table, so a board named differently in the
  two projects is a **false negative**, never a false positive.

**One alias error was found and corrected by the survey's own MCU
cross-check**: `Pixracer-periph` (STM32F427) had been aliased to
`mro/pixracerpro` (STM32H743). The row printed both MCUs side by side and the
mismatch was visible. That is the failure mode the design makes loud rather
than silent.
